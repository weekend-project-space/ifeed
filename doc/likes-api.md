# 喜欢接口与表结构

状态：后端三个接口及 PostgreSQL 存储已实现。目标数据库需执行 `V4__add_collections_and_likes.sql`，本文不代表目标数据库已经建表。

## 1. 接口概览

| 功能 | 方法 | 路径 |
|---|---|---|
| 新增喜欢 | POST | `/api/user/likes/{articleId}` |
| 删除喜欢 | DELETE | `/api/user/likes/{articleId}` |
| 喜欢列表（Pageable） | GET | `/api/user/likes` |

## 2. 通用约定

- 三个喜欢接口均要求 `Authorization: Bearer <token>`，用户身份由登录信息确定，请求不传 `userId`，只能操作和查询自己的喜欢记录。
- 响应体使用 JSON，时间使用 ISO 8601 UTC 格式，例如 `2026-09-21T08:00:00Z`。
- 请求中的 `articleId` 使用现有文章 UUID。服务端通过 `articles.uid` 查到内部 `articles.id`，之后的保存、删除和关联查询均使用数字 ID。
- 喜欢记录使用内部自增 `BIGINT id`，Java 对应 `Long`；`user_id`、`article_id` 也使用 `BIGINT`。不新增喜欢记录的 UUID，不对外暴露喜欢记录 ID。
- 同一用户对同一篇文章最多有一条喜欢记录。记录存在表示喜欢，不存在表示未喜欢；取消喜欢直接删除记录。
- 喜欢与收藏相互独立。一篇文章可以同时被喜欢和收藏，取消其中一种状态不影响另一种状态。
- 喜欢不包含文件夹；文件夹仅用于[收藏功能](collections-api.md)。

## 3. 新增喜欢

`POST /api/user/likes/{articleId}`

路径参数 `articleId` 为文章 UUID，请求体无。

### 行为

- 文章必须存在，不存在返回 `404`。
- 首次喜欢创建记录，`likedAt` 为服务端当前时间。
- 已喜欢时直接返回已有记录，不重复插入，也不更新 `likedAt`。
- 取消后再次喜欢会创建新记录，生成新的 `likedAt`。
- 通过 `(user_id, article_id)` 唯一约束保证并发请求不会产生重复记录；重复请求按成功处理，不将唯一约束冲突返回为 `409`。

### 响应：200 OK

```json
{
  "articleId": "7c3db9d8-10a0-4a69-9f3c-2f1b1d0b7d22",
  "liked": true,
  "likedAt": "2026-09-21T08:00:00Z"
}
```

## 4. 删除喜欢

`DELETE /api/user/likes/{articleId}`

路径参数 `articleId` 为文章 UUID，请求体无。

删除当前用户对该文章的喜欢记录。未喜欢、已经取消或文章已经物理删除时均返回成功；`articleId` 格式不合法仍返回 `400`。

### 响应：200 OK

```json
{
  "message": "Article unliked."
}
```

## 5. 喜欢列表（Pageable）

`GET /api/user/likes?page=0&size=20&sort=likedAt,desc`

只返回当前用户仍处于喜欢状态的文章，使用 Spring Data `Pageable` 参数和 `Page` 风格响应。

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `page` | integer | `0` | 从 0 开始，必须大于等于 0 |
| `size` | integer | `20` | 每页 1～100 条 |
| `sort` | string | `likedAt,desc` | 支持 `likedAt,asc` 或 `likedAt,desc`，沿用 Pageable 参数形式 |

- 未指定排序方向时按 `asc`；不支持的字段或方向返回 `400`。服务端追加内部 `id ASC`，保证喜欢时间相同时顺序稳定。
- 分页响应字段与收藏列表一致，页码字段为 `number`。下面仅展示五个主要分页字段，其余沿用 Spring Data `Page` 格式。
- 空列表的 `totalElements`、`totalPages` 均为 `0`；超出末页时返回空 `content`，总数仍为实际匹配数量。
- 文章展示字段允许因元信息缺失而为 `null`，不应导致整个列表报错。文章物理删除后，对应喜欢记录由外键级联删除，不再计入列表和总数。

### 响应：200 OK

```json
{
  "content": [
    {
      "articleId": "7c3db9d8-10a0-4a69-9f3c-2f1b1d0b7d22",
      "title": "PostgreSQL 索引使用指南",
      "feedTitle": "技术周刊",
      "thumbnail": "https://example.com/cover.jpg",
      "summary": "介绍常见索引的使用方式。",
      "likedAt": "2026-09-21T08:00:00Z"
    }
  ],
  "totalElements": 1,
  "totalPages": 1,
  "number": 0,
  "size": 20
}
```

## 6. PostgreSQL 表结构

新增表 `user_likes`，只保存当前有效的喜欢关系。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | 否 | 自增主键，内部 `Long` ID，不对外暴露 |
| `user_id` | `BIGINT` | 否 | 关联 `users.id` |
| `article_id` | `BIGINT` | 否 | 关联 `articles.id`，不保存文章 UUID |
| `liked_at` | `TIMESTAMPTZ` | 否 | 本次喜欢关系的创建时间，重复喜欢不更新 |

### 建表 SQL

以下 SQL 依赖已有的 `users`、`articles` 表，已纳入 `V4__add_collections_and_likes.sql`。

```sql
CREATE TABLE user_likes (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    article_id BIGINT NOT NULL,
    liked_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_user_likes_user_article UNIQUE (user_id, article_id),
    CONSTRAINT fk_user_likes_user
        FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT fk_user_likes_article
        FOREIGN KEY (article_id) REFERENCES articles (id) ON DELETE CASCADE
);

CREATE INDEX idx_user_likes_user_liked
    ON user_likes (user_id, liked_at DESC, id ASC);

CREATE INDEX idx_user_likes_article
    ON user_likes (article_id);
```

### 约束和索引用途

- `(user_id, article_id)` 唯一约束防止重复喜欢，自动创建的索引也用于查询喜欢状态、取消喜欢，无需重复建索引。
- `(user_id, liked_at DESC, id ASC)` 索引用于当前用户喜欢列表的默认分页排序。
- `article_id` 索引用于按文章查找喜欢记录，以及文章删除时的级联清理。
- 删除用户或物理删除文章时，级联删除对应喜欢记录。
- 喜欢表不增加 `uid`、`liked` 或删除标记；当前状态由记录是否存在确定。

与收藏表设计一致：新表主键及关联字段全部为 `BIGINT`／Java `Long`。现有 `Article.id` 已为 `Long`，`User.id` 仍为 `Integer`；PostgreSQL 支持 `BIGINT user_id` 外键引用现有 `INTEGER users.id`，应用边界需做数值类型转换。统一现有用户主键为 `Long` 属于单独的迁移工作。

## 7. 与 Interaction 的关系

文章详情 `GET /api/articles/{articleId}` 同时返回当前用户的 `liked`、`collected` 和 `folderId`，用于页面初始化按钮状态。未登录时两个状态为 `false`，`folderId` 为 `null`。此为已有文章详情接口的响应扩展，喜欢仍只有新增、删除、分页列表三个接口。

现有系统没有独立的喜欢状态数据，本次仅创建空的 `user_likes` 表，不从旧收藏或 Interaction 推断用户是否喜欢。原 MongoDB 数据不删除。

喜欢状态以 PostgreSQL 的 `user_likes` 为准。现有 `Interaction` 表达行为历史，后续需要为推荐记录喜欢、取消喜欢事件时，可在状态变更成功后接入，并处理事件投递的一致性。重复喜欢或重复取消没有产生实际状态变化时，不应重复产生行为事件。当前这版接口和表结构可以独立使用，无需依赖事件写入。

## 8. 错误响应

沿用项目的 `ErrorResponse` 格式：

```json
{
  "timestamp": "2026-09-21T08:00:00Z",
  "status": 404,
  "error": "Not Found",
  "message": "Article not found.",
  "path": "/api/user/likes/7c3db9d8-10a0-4a69-9f3c-2f1b1d0b7d22"
}
```

| 状态码 | 场景 |
|---|---|
| `400` | UUID 格式错误、分页或排序参数不合法 |
| `401` | 喜欢接口未登录或登录已失效 |
| `404` | 喜欢文章时文章不存在 |
| `500` | 服务端异常 |

重复喜欢、重复取消喜欢均返回成功，不返回 `409` 或 `404`；取消不存在文章的喜欢也返回成功。

## 9. 推荐信号

### 阅读序列加权

`PgUserSequenceStore` 仍以 PostgreSQL 最近阅读记录为序列来源，默认窗口为 30 天。文章顺序、阅读时间、已读排除规则和 I2I 随机选种逻辑保持不变，不把仅喜欢或仅收藏但未阅读的文章加入阅读序列。

对返回序列中的文章，分别批量查询当前用户的喜欢、收藏状态，使用内部 `Long` 文章 ID 关联，不逐篇查询。每次非空序列新增两次 SQL 查询，空序列不查询喜欢和收藏。

```text
weight = recencyWeight * (1 + interactionWeight + collectionBonus + likeBonus)
```

- 有效收藏默认加 `2`，有效喜欢默认加 `2`，二者可以叠加；没有对应关系时加 `0`。
- 暂不考虑原有交互加权和衰减时，普通阅读、喜欢、收藏、同时喜欢和收藏的基础分分别为 `1 / 3 / 3 / 5`。
- 原有 MongoDB Interaction 次数加权、估算阅读时长保持不变。喜欢和收藏不会增加估算阅读时长，也不从 Interaction 推断当前喜欢或收藏状态。
- I2I 选中某篇文章作为种子后，其相似文章得分使用增强后的权重；本次不提高该文章被随机选为种子的概率。

### 兴趣画像

`UserInterestProfileService` 合并阅读、收藏和喜欢的文章，以内部文章 ID 去重，每篇文章只计算一次基础分，再叠加收藏、喜欢加分。喜欢默认查询最近 90 天，最多取本次 `lookback` 指定的数量，未指定时默认 `200`；仅喜欢但未阅读的文章也可以贡献兴趣画像。

所有来源参与来源、标签、分类偏好计算。阅读或喜欢的文章还参与关键词、实体提取，仍受对应提取开关控制。仅收藏文章的提取行为保持原样。各属性维度沿用现有归一化、阈值和结果数量限制；原有 `lookback < 10` 时不读取收藏的规则也保持不变。

画像加分依据各来源时间窗口及数量限制内的记录；与阅读序列查询当前喜欢、收藏状态的方式不同。取消喜欢或收藏后，在下一次实际计算序列或画像时不再使用对应加分，本次不主动清除已经生成的推荐结果或缓存。

### 配置

以下为实际读取的配置路径，`recall` 必须放在 YAML 顶层，不是 `app.recall`。现有配置中的 `app.recall.preference` 不会覆盖这些值，本次未调整该配置层级。

```yaml
recall:
  sequence:
    collection-bonus: 2.0
    like-bonus: 2.0
  preference:
    collection-bonus: 2.0
    like-bonus: 2.0
    like-window-days: 90
```

序列和画像的加分可分别调整。默认值是初始参数，推荐效果仍需通过实际数据评估。本次复用现有 PostgreSQL 表，不新增接口、表结构或数据迁移，也不向 Interaction 写入新事件。
